# dsh-superagent 设计采纳计划

状态：**SA1、SA2 和 PI4 已实现**（[effects](../../effects)、[background](../../background)），实施差异和已知限制见“实施记录”。2026-11-02。依据 [dsh-superagent `6337fc8`](https://github.com/deepseek-ai/dsh-superagent-prototype/tree/6337fc823ce20251c8de8085948165c81aaa701e) 的 `docs/003-execution.md` 与 `docs/007-architecture.md`。对方自称研究原型，这里只读过设计文档，未核对其源码，也未运行。

dsh-superagent 是建在 DeepSeek Harness 之上的主动式应用，与本仓库不在同一层。本计划只采纳下面两项机制，不引入 Ticket、Eval、Source、面板等应用层概念。Worker 免审批的执行方式不采纳，现有沙盒与审批不变。

## 阶段

| 阶段 | 归属 | 依赖 | 交付（提案） | 主要验收 |
| --- | --- | --- | --- | --- |
| SA1 外部副作用投递 | 可选包 `effects` | [PI1](PI_AGENT_ADOPTION_PLAN.md) | 决定与待办原子写入、提交后执行、失败退避 | 各崩溃点不丢失待办，不确定的操作不自动重做 |
| SA2 后台子工作的运行规则 | 可选包 `background`，同时实现 [PI4](PI_AGENT_ADOPTION_PLAN.md#pi4持久子工作所有权) | PI1 | 完成通知、等待上限、并发槽位 | 通知只消费一次，新任务占满槽位时人的输入仍能进入 |

## SA1：外部副作用投递

已有能力：`durable.OperationPolicy` 的 `Reconcile` 核对中断的操作，`ErrOperationAttention` 和 `ErrUnconfirmed` 保留结果未知的状态。这些解决“工具调用如何重放”。

缺口：Harness 与 GoAgent 都没有把“决定做某事”和“待执行的动作”一起提交的队列。宿主在决定后发送消息或 PR 评论时，如果进程在两者之间崩溃，就会丢失动作，或重复执行。

拟定契约：

- 决定与待办在同一事务内写入，提交后才执行；回滚不留下待办。
- 同一 `kind/key` 只有一条待办；等待中再次入队时替换内容，不改变排队位置。
- 失败按退避重试；推迟（如没有空闲槽位）不计入失败次数。
- 同一目标的消息保持顺序；一条消息持续失败时暴露为问题，不无限阻塞其他目标。
- 不承诺恰好一次。执行结果未知时沿用 `Reconcile` 和 `ErrUnconfirmed`，投递重试与业务重放分开。

恢复时可以提示 Agent 先检查目录、Git 和外部系统，再决定是否重做。这只是补充，不能替代 `Reconcile` 或 `MaxAttempts=1` 的确定性约束，因为模型可能不照做。

原子范围：GoAgent v0.36.0 起，`durable.Store.SaveAll` 和 `session.Store.AppendAll` 支持跨 ID 的原子提交，决定与待办可以分开存放。调用方须持有全部 ID 的锁，作用域视图不跨作用域。

验收至少覆盖：

1. 事务回滚后没有待办；提交后、执行前崩溃，重启后仍会执行。
2. 执行后、标记完成前崩溃，先核对再决定，不盲目重发。
3. 合并、顺序、退避和推迟计数的行为确定，用可计数的外部副作用验证。
4. 不确定的操作不因重启自动重跑。

## SA2：后台子工作的运行规则

已有能力：GoAgent v0.36.0 起，持久运行中 `builder.Handle` 的输入写入持久收件箱后才算接受，重启后恢复未领取的输入并继续 Followup 轮次；Preset 子 Agent 仍同步返回；PI4 已规划前台与后台、所有者、租约、预算和结果投递。本阶段不重复这些内容，只补充 PI4 未定义的运行规则。

拟定规则（括号内是 dsh-superagent 的取值，仅供参考，不作为默认值）：

- **完成通知：** 后台工作的结果先持久记录，再通知所有者，通知可以由记录重新生成。轮次全部结束后，`Handle` 的输入方法都返回 `ErrHandleDone`，也不会自行开启新轮次，所以由宿主决定如何投递，不能静默丢弃。
- **空闲判定：** 轮次结束但仍有后台工作时，不算空闲，也不报告“等待中”。
- **等待上限：** 轮次结束后，后台工作的等待时间有上限（30 分钟）。到期时终止并报告，已知结果在下一轮可读。
- **交接给人：** 交接后立即释放槽位，子 Agent 停止，已交付的报告继续有效。
- **并发槽位：** 轮次占用槽位，并为人的输入多留一个（1 个）。新任务和自动输入（如 CI 结果）只用普通槽位，因此不会挡住人。

权限、预算、网络和沙箱继续沿用 PI4 的向后代收窄要求，后台运行不放宽任何上限。

验收至少覆盖：

1. 轮次结束、取消和关闭与完成通知竞争时，通知只消费一次，不重新执行业务。
2. 等待到期后的状态和报告确定，重启后行为一致。
3. 普通槽位占满时，人的输入可以立即进入，自动输入继续排队。
4. 进程退出时不留下无所有者的后台工作。

## 边界

### 职责

| 层 | 负责 | 不负责 |
| --- | --- | --- |
| GoAgent | 持久存储、操作重放、`Handle` 与收件箱 | 外部系统、业务路由、队列的投递目标 |
| Harness | 装配、后台工作运行规则、权限和预算向后代收窄 | 租户治理、对外账号、具体业务的核对逻辑 |
| 宿主 | 投递目标和凭据、`Reconcile` 的业务实现、轮次结束后的通知去向 | 绕过 Harness 的上限 |

### 安全

- 待办和通知的内容是数据，不授予权限，也不能修改策略或扩大目标范围。
- 待办不保存秘密，凭据在执行时由宿主解析；错误和审计记录同样不写入秘密。
- 执行待办前按当前策略重新校验。策略变化后不再允许的待办应撤销并留下记录，不能沿用入队时的授权。
- 恢复或重试不复用已消费的单次批准，后台运行也不放宽沙箱、网络和预算上限。
- 队列长度、单条内容大小和尝试次数都有上限。超限时入队失败并报错，不静默截断。

### SA1 的边界情况

| 情况 | 要求 |
| --- | --- |
| 待办正在执行时再次入队 | 不替换执行中的内容，新内容排在其后 |
| 目标暂时停用 | 待办继续等待，不计入失败 |
| 目标永久失效（如会话已删除） | 撤销并保留时间和原因，不再重新排队 |
| 结果未知（如超时后连接断开） | 进入核对，不算失败也不算成功；无法核对时交给宿主 |
| 写入时已失去运行锁（`ErrLeaseLost`） | 旧持有者立即停止，不继续执行待办 |
| 进程关闭 | 停止领取新待办，未完成的保留到下次启动 |

### SA2 的边界情况

| 情况 | 要求 |
| --- | --- |
| 通知到达时 `Handle` 已结束 | 由宿主按持久结果投递；未投递的通知保持可查询 |
| 通知未被领取时进程崩溃 | 持久运行中由收件箱恢复；非持久运行的通知随进程丢失，从持久结果重新生成，按 child run 身份去重 |
| 通知已被领取，但模型请求随后失败 | 领取不等于送达，也不等于已处理；未进入持久历史的须重新投递 |
| 迭代或预算已耗尽 | 新轮次不绕过限制；结果保留并报告，等宿主处理 |
| 等待到期与工作完成同时发生 | 以先持久记录的结果为准，不能既报告完成又报告被终止 |
| 持久运行中到达新输入 | `Redirect` 沿用现有行为降级为 Steer，不取消进行中的模型回合 |
| 为人保留的槽位已被占用 | 人的输入排在下一个空闲槽位之前，不抢占进行中的轮次；自动输入不得使用保留槽位 |

## 实施记录（2026-11-02）

与上文提案的差异：

| 提案 | 实施 | 原因 |
| --- | --- | --- |
| SA1 先做宿主案例 | 直接提供 `effects` 包 | SA2 的通知投递就是它的第一个使用方 |
| 决定与待办可以分开存放 | 队列是单个快照，待办数量和内容大小有上限 | `durable.Store` 不能枚举，单个快照才能取到全部待办 |
| 同目标持续失败时不阻塞 | 结果未知的待办同样不阻塞后续待办，由 `Problems` 暴露 | 阻塞要等宿主裁决，可能无限等待；同键的新待办会被拒绝 |
| 按人保留槽位 | 普通槽位外多一个，等待时人的输入优先于自动输入，再优先于新任务 | 与提案一致，取值固定为 1 个 |
| 通知由 child run 身份去重 | 投递至少一次，每次状态变化有新的 `Generation`；`NotifyHandle` 用 `Handle.SteerOnce` 去重 | 去重键与输入须原子落盘，只在 Harness 里无法判断崩溃前是否已写入 |

PI4 的实现结果：

- **沙箱责任：** 持有托管沙箱的后台 child 每次运行单独装配，实例归 child：进程停止时保留，重启后连回，结束时销毁。宿主用 `Registry.Resolve` 借出或保留的实例由宿主负责。不用托管沙箱的目标 preset 仍共用一个 Assembly。
- **中间层上限：** 沙箱和网络上限在没有 workspace 的中间层也会传递，前台由 `TestReviewGrandchildCannotLoseAncestorCeilings` 覆盖，后台由 `TestBackgroundGrandchildCannotLoseAncestorCeilings` 覆盖。此前把这项记为未实现是错误的。
- **预算：** 重启后从记录恢复，继续计入同一份账本。这是接入时漏掉的：重启后没有父调用的 ctx，上限曾因此消失。
- **审批：** 后台 child 不调用同步的 `Host.Approver`，需要审批时进入 `waiting`。批准只放行这一次调用，不留下会话授权，也不落盘；`approval: never` 仍然优先。
- **策略变更：** child 把装配清单固定在自己的日志里，恢复时不一致就记为失败（`manifest_changed`），不按新策略继续旧记录。

已知限制：

- 用 `BuilderRunner` 时，停在模型请求中途的子工作重启后重发这次请求，同一回合最多 3 次。被打断的请求可能已经计费，所以可能重复计费，每次重发各占一份预算。自定义 `RunAgent` 须自行开启 `WithInterruptedModelResend`。
- 后端实现 `KeyedExecutor` 时，`run_command` 重启后附着到原命令并取回结果，副作用只有一次；命令丢失（容器重启、状态被删）时不重跑，由模型检查后决定。没有这项能力的后端和 `git_commit`、文件修改工具停在中途时，子工作记为 `failed`（`attention`），文件和容器不会丢，但工作不会自动继续。这些情况都有真实 Docker 测试。
- 重启后第一次连接实例就遇到网络错误时，子工作记为 `failed`（`execution`）并回收实例，不会等网络恢复再试。
- Provider 没有实现 `sandbox.InstanceFinder` 时，分配中崩溃无法判断实例是否存在：子工作失败（`sandbox_unknown`），这条释放进入 `Manager.Problems` 由宿主处理。可能误报，不会漏报。
- `CheckPolicy` 推迟到每次运行：后端不满足策略时子工作失败，`Build` 不报错。
- 内层后台 child 的权限上限来自外层的模板装配，不是外层某次运行：宿主在外层运行中用 `Assembly.Permissions` 收窄的会话模式不会传给内层。
- 通知只在同一执行键内去重。宿主换执行键开新运行时，新运行可能再收到一次：旧收件箱里未领取的输入不会带到新运行，这时重投是必要的，Harness 无法判断新对话里是否已有这条通知。

验证范围：`effects` 和 `background` 的单元测试使用 `FileStore`，不校验锁的持有者；等待、重启、续跑、资源释放、租约接管和通知去重由 `integration/postgres` 在真实 Postgres 上验证；托管沙箱的生命周期由 `integration` 中的测试用 Provider 在真实 Docker 容器上验证，包括真实进程崩溃。两者都在 CI 运行。`sandboxtest` 是任何 Provider 都能运行的契约测试，`sandboxtest.Faults` 模拟响应丢失和连接失败，Docker 和自托管 OpenSandbox 的测试 Provider 都已通过。云厂商的 Provider 仍然没有验证过，下一步见 [沙箱路线图](SANDBOX_ROADMAP.md)。
