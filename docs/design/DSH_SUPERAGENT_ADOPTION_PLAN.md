# dsh-superagent 设计采纳计划

状态：**调研提案，功能阶段未执行**。2026-11-02。依据 [dsh-superagent `6337fc8`](https://github.com/deepseek-ai/dsh-superagent-prototype/tree/6337fc823ce20251c8de8085948165c81aaa701e) 的 `docs/003-execution.md` 与 `docs/007-architecture.md`。对方自称研究原型，这里只读过设计文档，未核对其源码，也未运行。

dsh-superagent 是建在 DeepSeek Harness 之上的主动式应用，与本仓库不在同一层。本计划只采纳下面两项机制，不引入 Ticket、Eval、Source、面板等应用层概念。Worker 免审批的执行方式不采纳，现有沙盒与审批不变。

| 阶段 | 归属 | 依赖 | 交付（提案） | 主要验收 |
| --- | --- | --- | --- | --- |

## SA1：外部副作用投递

已有能力：`durable.OperationPolicy` 的 `Reconcile` 核对中断的操作，`ErrOperationAttention` 和 `ErrUnconfirmed` 保留结果未知的状态。这些解决“工具调用如何重放”。

缺口：Harness 与 GoAgent 都没有把“决定做某事”和“待执行的动作”一起提交的队列。宿主在决定后发送消息或 PR 评论时，如果进程在两者之间崩溃，就会丢失动作，或重复执行。

拟定契约：

- 决定与待办在同一事务内写入，提交后才执行；回滚不留下待办。
- 同一 `kind/key` 只有一条待办；等待中再次入队时替换内容，不改变排队位置。
- 失败按退避重试；推迟（如没有空闲槽位）不计入失败次数。
- 同一目标的消息保持顺序；一条消息持续失败时暴露为问题，不无限阻塞其他目标。
- 不承诺恰好一次。执行结果未知时沿用 `Reconcile` 和 `ErrUnconfirmed`，投递重试与业务重放分开。

恢复时可以提示 Agent 先检查目录、Git 和外部系统，再决定是否重做。这只是补充，不能替代 `Reconcile` 或 `MaxAttempts=1` 的确定性约束，因为模型可能不照做。

原子范围：GoAgent v0.36.0 起，`durable.Store.SaveAll` 和 `session.Store.AppendAll` 支持跨 ID 的原子提交，决定与待办可以分开存放。调用方须持有全部 ID 的锁，作用域视图不跨作用域。

验收至少覆盖：

1. 事务回滚后没有待办；提交后、执行前崩溃，重启后仍会执行。
2. 执行后、标记完成前崩溃，先核对再决定，不盲目重发。
3. 合并、顺序、退避和推迟计数的行为确定，用可计数的外部副作用验证。
4. 不确定的操作不因重启自动重跑。

## SA2：后台子工作的运行规则

已有能力：GoAgent v0.36.0 起，持久运行中 `builder.Handle` 的输入写入持久收件箱后才算接受，重启后恢复未领取的输入并继续 Followup 轮次；Preset 子 Agent 仍同步返回；PI4 已规划前台与后台、所有者、租约、预算和结果投递。本阶段不重复这些内容，只补充 PI4 未定义的运行规则。

拟定规则（括号内是 dsh-superagent 的取值，仅供参考，不作为默认值）：

- **完成通知：** 后台工作的结果先持久记录，再通知所有者，通知可以由记录重新生成。轮次全部结束后，`Handle` 的输入方法都返回 `ErrHandleDone`，也不会自行开启新轮次，所以由宿主决定如何投递，不能静默丢弃。
- **空闲判定：** 轮次结束但仍有后台工作时，不算空闲，也不报告“等待中”。
- **等待上限：** 轮次结束后，后台工作的等待时间有上限（30 分钟）。到期时终止并报告，已知结果在下一轮可读。
- **交接给人：** 交接后立即释放槽位，子 Agent 停止，已交付的报告继续有效。
- **并发槽位：** 轮次占用槽位，并为人的输入多留一个（1 个）。新任务和自动输入（如 CI 结果）只用普通槽位，因此不会挡住人。

权限、预算、网络和沙箱继续沿用 PI4 的向后代收窄要求，后台运行不放宽任何上限。

验收至少覆盖：

1. 轮次结束、取消和关闭与完成通知竞争时，通知只消费一次，不重新执行业务。
2. 等待到期后的状态和报告确定，重启后行为一致。
3. 普通槽位占满时，人的输入可以立即进入，自动输入继续排队。
4. 进程退出时不留下无所有者的后台工作。

## 边界

### 职责

| 层 | 负责 | 不负责 |
| --- | --- | --- |
| GoAgent | 持久存储、操作重放、`Handle` 与收件箱 | 外部系统、业务路由、队列的投递目标 |
| Harness | 装配、后台工作运行规则、权限和预算向后代收窄 | 租户治理、对外账号、具体业务的核对逻辑 |
| 宿主 | 投递目标和凭据、`Reconcile` 的业务实现、轮次结束后的通知去向 | 绕过 Harness 的上限 |

### 安全

- 待办和通知的内容是数据，不授予权限，也不能修改策略或扩大目标范围。
- 待办不保存秘密，凭据在执行时由宿主解析；错误和审计记录同样不写入秘密。
- 执行待办前按当前策略重新校验。策略变化后不再允许的待办应撤销并留下记录，不能沿用入队时的授权。
- 恢复或重试不复用已消费的单次批准，后台运行也不放宽沙箱、网络和预算上限。
- 队列长度、单条内容大小和尝试次数都有上限。超限时入队失败并报错，不静默截断。

### SA1 的边界情况

| 情况 | 要求 |
| --- | --- |
| 待办正在执行时再次入队 | 不替换执行中的内容，新内容排在其后 |
| 目标暂时停用 | 待办继续等待，不计入失败 |
| 目标永久失效（如会话已删除） | 撤销并保留时间和原因，不再重新排队 |
| 结果未知（如超时后连接断开） | 进入核对，不算失败也不算成功；无法核对时交给宿主 |
| 写入时已失去运行锁（`ErrLeaseLost`） | 旧持有者立即停止，不继续执行待办 |
| 进程关闭 | 停止领取新待办，未完成的保留到下次启动 |

### SA2 的边界情况

| 情况 | 要求 |
| --- | --- |
| 通知到达时 `Handle` 已结束 | 由宿主按持久结果投递；未投递的通知保持可查询 |
| 通知未被领取时进程崩溃 | 持久运行中由收件箱恢复；非持久运行的通知随进程丢失，从持久结果重新生成，按 child run 身份去重 |
| 通知已被领取，但模型请求随后失败 | 领取不等于送达，也不等于已处理；未进入持久历史的须重新投递 |
| 迭代或预算已耗尽 | 新轮次不绕过限制；结果保留并报告，等宿主处理 |
| 等待到期与工作完成同时发生 | 以先持久记录的结果为准，不能既报告完成又报告被终止 |
| 持久运行中到达新输入 | `Redirect` 沿用现有行为降级为 Steer，不取消进行中的模型回合 |
| 为人保留的槽位已被占用 | 人的输入排在下一个空闲槽位之前，不抢占进行中的轮次；自动输入不得使用保留槽位 |
